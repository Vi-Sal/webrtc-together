01 / Direction

One community. Many ways to connect.

Create a community (the product concept often called a “server”), organize text and voice channels inside it, and let members move naturally from messages into a video conversation. A community is a database entity; it does not require a dedicated physical server.

Your repository today

Java 21, Gradle, Spring Boot, MVC and WebSocket dependencies. A GET /greeting endpoint and a context-load test provide the starting point. Authentication, persistence, calling, and a frontend are still to be built.

The first useful release

Sign in → create a community → invite a friend → join a voice channel → enable cameras → exchange messages → leave cleanly. Make this journey reliable before expanding the feature set.

This page is a planning and learning artifact. The feature phases below are recommendations, not claims of exact Discord or Telegram feature parity.

03 / Mental model

Learn the pieces behind a call.

Capture → negotiate → connect

getUserMedia() asks for camera and microphone access. RTCPeerConnection carries media. An SDP offer/answer describes the session; ICE candidates describe possible network paths.

Your application supplies signaling to exchange these messages. For a learning demo, use Spring WebSocket with authenticated recipient routing. WebRTC peer connection guide.

STUN, TURN, and SFU

STUN helps discover a public-facing address. TURN relays traffic when direct connectivity fails. An SFU forwards published media tracks to other participants, avoiding a separate upload to every peer.

TURN remains relevant with an SFU for restrictive networks. Connectivity basics · LiveKit SFU architecture.

Learning lab: build one raw WebRTC call
  1. Serve two browser clients on localhost or HTTPS, request media after a user action, and display a muted local preview.
  2. Create a peer connection with working ICE servers; add local tracks and render incoming tracks.
  3. Exchange offer, answer and trickled ICE candidates through a Spring WebSocket endpoint. Queue remote candidates until a remote description exists.
  4. Use the perfect negotiation pattern to handle simultaneous offers.
  5. On hang-up, stop local tracks, close the connection, remove listeners, and notify the other participant. Test separate devices and networks, including forced TURN relay.
Two deliberate paths: raw WebRTC teaches the protocol. For the community app, adopt the LiveKit SDK for media signaling and room connections. Spring continues to own application rules and durable chat; you do not need to recreate LiveKit signaling in STOMP.
04 / System design

Keep application logic and media routing separate.

↔

↔

↔
Browser B … NSubscribe to tracks

Media can traverse TURN when needed. Spring calls LiveKit server APIs for tokens and moderation; verified LiveKit webhooks update application call state. Redis is an optional presence/cache component as the app grows.

  1. The signed-in browser requests POST /api/channels/{id}/call-token.
  2. Spring verifies membership, channel permissions, bans, and capacity, then derives the media room name and participant identity itself.
  3. Spring issues a short-lived, room-scoped token using server-held credentials. The browser connects directly to LiveKit with it. See token endpoint examples, including Spring Boot.
  4. The SDK publishes selected camera/mic tracks and subscribes to peers. Durable text chat uses Spring and PostgreSQL.
  5. On kick or permission change, update application authorization and remove the active participant through the media server API. Token expiry alone does not disconnect an established session.

Deployment shape: begin with one Spring application, one database, a frontend deployment, and managed LiveKit or one self-hosted instance. Self-hosted media needs publicly reachable network paths, TLS and appropriate firewall rules; ordinary HTTP reverse proxying alone is insufficient. Self-hosting documentation.

Scaling boundary: Spring’s in-memory STOMP broker is suitable for an initial single instance. Before adding application replicas, design shared message delivery (for example, an external STOMP broker relay), presence expiry, and reconnect history recovery. Redis alone does not turn the simple broker into a distributed broker. Spring STOMP documentation.

Dependency rule: controllers and WebSocket handlers call services; services enforce permissions and use repositories or media adapters. Do not expose JPA entities directly as API responses or store active media tracks in the database.

07 / Contracts

Model membership before the video button.

Core records

  • User: id, identity subject, display name, avatar key.
  • Community and Membership: owner, user, role; unique community/user pair.
  • Channel: community, type TEXT/VOICE, visibility and capacity.
  • Message: channel, author, body, timestamps, client request ID.
  • Invite: hashed code, expiry, usage limit.
  • CallSession: channel, media room reference, start/end; optional participant history with retention limits.

Use indexed cursor pagination for messages. Track unread state with a member’s last-read message position. Treat presence as expiring ephemeral state.

Proposed endpoints

  • GET /api/me
  • POST /api/communities
  • POST /api/communities/{id}/invites
  • POST /api/invites/{code}/accept
  • GET /api/channels/{id}/messages?before=…
  • POST /api/channels/{id}/messages
  • POST /api/channels/{id}/call-token
  • POST /api/media/webhooks

Choose REST writes + WebSocket events for the first chat implementation. Do not independently implement two conflicting message-write paths.

// Proposed server event, delivered after the database commit
{
  "type": "message.created",
  "eventId": "evt_123",
  "channelId": "channel_456",
  "occurredAt": "2026-09-25T12:00:00Z",
  "payload": {
    "id": "msg_789",
    "authorId": "user_42",

    "body": "Ready to join?"

Authorize both SEND and SUBSCRIBE destinations, derive sender identity from the authenticated session, and reject client attempts to impersonate another user. Deduplicate retries by user and client request ID. Reconnect clients recover missed messages from the database; later, use a transactional outbox when reliable event publication across failures is required. Spring WebSocket security.

08 / Interaction design

Make the call feel effortless.

The community shell

Desktop: community rail → channel list → conversation/call canvas → optional member panel. Mobile: one primary panel with a channel drawer and persistent compact call controls. Keep the active call alive when navigating between text channels.

Use consistent spacing, readable text, restrained motion and clear unread markers. Virtualize long histories, preserve scroll position when loading older messages, and reconcile optimistic messages with server IDs.

The call experience

Show a pre-join preview, device selectors and an explicit Join action. Prioritize the active speaker or shared screen, with a filmstrip for others. Keep mute, camera, share and leave controls stable and labeled.

Expose permission denied, no device, joining, reconnecting, disconnected and audio-only fallback states. Announce important changes accessibly and offer a user action when autoplay blocks remote audio.

Screen sharing and browser limits

Start sharing from a user gesture with getDisplayMedia(); the browser controls source selection. Shared system audio depends on the browser and selected source. Handle the track’s ended event when users stop sharing from browser chrome. Screen capture reference.

Quality, measurement and cost

Use adaptive subscriptions and appropriate video layers instead of sending full-resolution video to every tiny tile. Record call join success, time to first remote audio/video, packet loss, jitter, round-trip time, reconnects and TURN usage. Start with a small tested room cap and raise it from measurements; do not promise a participant count without load tests. Bandwidth egress, TURN relaying and recording storage are major cost drivers.

Privacy and access boundaries

Use HTTPS/WSS, narrowly scoped room tokens and explicit origin/CSRF rules. Never ship media server secrets to the frontend. Verify webhook signatures and make processing idempotent. WebRTC transport encryption is not automatically participant-only E2EE through an SFU. An E2EE mode needs key distribution and compatibility decisions, especially for server-side recording and transcription. LiveKit encryption model.

09 / Build order

Ship in learning-sized milestones.

Checkpoints are a local worksheet for this page session; they reset on reload.

Commands available right now

./gradlew bootRun     # Run the existing Spring application
./gradlew test        # Run existing backend tests
./gradlew build       # Compile, test and package

After scaffolding frontend/ with the React TypeScript Vite template, document its install/dev/build commands and required environment variables. Keep identity credentials, database passwords and LiveKit secrets outside version control.

Test beyond localhost: use Chrome, Firefox and Safari plus real mobile devices; exercise Wi-Fi/mobile transitions, poor bandwidth, simultaneous joins, unauthorized subscriptions and duplicate/out-of-order webhooks. Automated fake media helps CI, but does not replace real camera, audio and network checks.
